## 1. 为什么用 epoll，而不用 select / poll？

**一句话结论**：select 每次调用都要把全部 fd 检查一遍；epoll 只处理已经就绪的那几个，开销与连接总数无关。

**select 怎么做**

1. 程序把「关心的所有 fd」打进一个位图 `fd_set`，每次调用前都要重新构造。
2. 程序把位图交给内核，内核从头到尾检查每一个 fd。
3. 内核把位图改写为「只保留就绪的」，返回就绪个数。
4. 程序再遍历一遍位图，用 `FD_ISSET` 找出到底是哪几个。
5. 位图最大只有 `FD_SETSIZE` = 1024 个 fd。

**为什么慢**

- 每次调用都要重新拷贝整个集合（用户态到内核态，再拷回来）。
- 内核要遍历全部 fd，连接越多越慢。
- 内核返回后，程序还要自己再遍历一遍才能找出是谁。
- 有 1024 的硬上限。

**epoll 怎么做**

1. `epoll_create` 创建一个内核对象，里面有一棵红黑树（存注册过的 fd）和一条就绪链表。
2. `epoll_ctl(ADD)` 把 fd 插进红黑树，**同时**在这个 fd 的等待队列上挂一个回调函数。
3. 数据到达时，内核执行回调，把 fd 挂到就绪链表，并唤醒睡在 `epoll_wait` 的进程。
4. `epoll_wait` 只把就绪链表上的事件复制到 `events[]`，返回个数。

**代价**

内核要多维护红黑树和就绪链表，内存用得更多；换来的是时间更少——**空间换时间**。

## 2. ET 和 LT 的区别？ET 为什么必须循环读到 `EAGAIN`？

**一句话结论**：两者都是「新数据到达触发回调，把 fd 挂到就绪链表」。区别在**报告之后**：LT 把「还有数据」的 fd 放回链表，下次还报；ET 不放回，只有新数据到达才会再报。

**LT（水平触发）**

只要条件成立（缓冲区里还有数据），每次 `epoll_wait` 都会报告这个 fd。
所以程序读不完也没关系，下一次还会被通知。

**ET（边沿触发）**

只在「从无数据变成有数据」那一刻触发一次回调，报告完之后不再放回链表。
除非有新数据到达触发新的回调，否则不会再通知。

**ET 为什么必须循环读到 `EAGAIN`**

- ET 不会再通知，所以一次没读完，剩下的数据就**永远读不到**，连接表现为「假死」（不报错、不断开，就是没反应）。
- 所以必须在一个循环里反复 `recv`，直到返回 `-1` 且 `errno == EAGAIN`。
- `EAGAIN` 不是错误，它表示「缓冲区现在空了」——是循环退出的正常条件。

**为什么还必须非阻塞**

- 循环的最后一次 `recv` 时，缓冲区已经空了。
- 如果 fd 是阻塞的，这次 `recv` 会睡下去等新数据，**把线程占住**。
- 线程池只有 8 个线程，8 个空闲连接就能把线程占满。
- 非阻塞的 `recv` 会立刻返回 `EAGAIN`，让循环安全退出。

**两个要求是绑在一起的**：ET 不重复通知 → 必须一次读完 → 读到空会阻塞 → 所以必须非阻塞。

**代码位置**：`http_conn.cpp:198 read_once()`——LT 分支只 `recv` 一次；ET 分支用 `while(true)` 循环到 `EAGAIN`。

## 3. Reactor 和 Proactor 的区别？这个项目是哪种？

**一句话结论**：区别在于 `recv` 由谁调用。Reactor 由处理者自己调；Proactor 由操作系统读好之后再交给处理者。

**Reactor**

- 事件循环通知处理者：「fd 5 可读了」。
- 处理者（worker 线程）**自己**调 `recv` 把数据读出来，再处理。
- 通知的内容是**事件**。

**Proactor**

- 处理者先提交一个读请求，然后立刻返回。
- 操作系统在后台把数据读好，读完再把数据交给处理者。
- 处理者从头到尾**没有调用过 `recv`**。
- 通知的内容是**结果**。

**这个项目是哪种**

默认是 **Proactor**，证据有两处：

- `config.cpp:32`：`actor_model = 0` 是默认值。
- `webserver.cpp:304`：`if (1 == m_actormodel)` 是 Reactor 分支；0 不等于 1，所以走 `else`（Proactor）。

Proactor 分支里，主线程先调 `read_once()` 读数据，再用 `append_p()` 把任务交给 worker 解析。

**为什么这个「Proactor」反而让主线程更累**

因为它没有用操作系统的异步 I/O（比如 `io_uring`），用的还是普通的同步 `recv` / `writev`。
「替 worker 读好数据」这件事只能由主线程自己同步做，于是：

- 主线程：`accept` + `recv` + `writev` + `close`，包办了全部 socket I/O。
- worker：只做解析，几十微秒就干完。

结果主线程成为瓶颈：压测时线程从 8 加到 16，QPS 几乎不变（3937 对 3965）。

**优化方向**

退回真正的 Reactor（`-a 1`）让 worker 自己读；或者用 `io_uring` 做真正的 Proactor。

## 4. 线程池怎么实现的？任务队列用什么？怎么唤醒工作线程？

**一句话结论**：一个任务队列 + 一把互斥锁 + 一个信号量，8 个固定线程循环取任务。

**三样东西**

| 东西 | 作用 |
|---|---|
| `std::list<T*> m_workqueue` | 任务队列，装待处理的 `http_conn` 指针 |
| `pthread_mutex_t m_queuelocker` | 互斥锁，保证同一时刻只有一个线程操作这条链表 |
| `sem m_queuestat` | 信号量，数「队列里有多少任务」，初始值 0 |

**为什么锁和信号量都要**

- **只用信号量**：`std::list` 不是线程安全的，多个线程同时 `push_back` / `pop_front` 会破坏链表指针。
- **只用锁**：worker 只能不停加锁检查队列空不空（忙等），烧 CPU。
- 所以：**信号量负责「睡/醒」，锁负责「安全访问」**。

**加入任务（主线程做）**

```
lock → push_back(任务) → unlock → post()   // 信号量 +1，叫醒一个 worker
```

队列有上限 `max_request = 10000`，满了 `append` 返回 `false`。
注意：这个项目的三处调用都没有检查返回值，队列满了会**静默丢任务**，连接一直挂到定时器超时——这是一个真实缺陷。

**取任务（worker 做）**

```
wait()（没任务就睡）→ lock → front() → pop_front() → unlock → process()
```

`front()` 只是读出来，`pop_front()` 才真正删除，两步都必须在锁里。
否则两个线程可能 `front()` 到同一个任务，然后一个把它们都 `pop` 掉，另一个任务就丢了。

**信号量的含义**

- 值 = （累计入队任务数）−（累计 `wait` 次数）
- 值 **< 0**：`|值|` = 正在睡眠的线程数
- 值 **> 0**：值 = 队列里还没人取的任务数
- 初始值是 **0**，因为一开始队列是空的

**工作线程怎么工作**

每个 worker 都执行同一个 `run()` 死循环：`wait → 取任务 → process`。
**代码永远是同一份，变的是它从队列里拿到的那一个指针。**

## 5. 定时器用的什么结构？惰性删除是什么？

**结构：升序双向链表（不是最小堆）**

每个 `util_timer` 存 `expire`（到期时间戳）、回调函数、用户数据、`prev`/`next` 指针，
整条链表按 `expire` 从小到大排序，所以表头永远是最早到期的那个。

| 操作 | 做什么 | 复杂度 |
|---|---|---|
| `add_timer` | 遍历找位置插入 | O(n) |
| `adjust_timer` | 有数据来往时把超时时间往后推 | O(n) |
| `del_timer` | 双向链表改两个指针就摘掉 | O(1) |

**`tick()` 巡检**

从表头开始遍历，`expire <= 现在` 的执行回调并删除；遇到第一个未过期的就 `break`——
因为链表是升序的，后面的只会更晚，不用再看。

**怎么被触发：信号 → 管道 → epoll**

1. 启动时 `alarm(TIMESLOT)`，5 秒后内核发出 `SIGALRM`
2. 信号处理函数 `sig_handler` 只做一件事：把信号编号 `send` 进 `socketpair` 的一端，然后返回
3. 管道另一端早先已注册进 epoll，`epoll_wait` 发现它可读
4. `dealwithsignal()` 用 `recv` 读出信号编号，是 `SIGALRM` 就把 `timeout` 置为 `true`
5. 主循环调 `timer_handler()` → `tick()` 巡检 → 再 `alarm(TIMESLOT)` 重新上闹钟

**为什么要绕这一圈**

信号处理函数是**异步打断**的，可能打断主线程正在进行的 `malloc`/`free`。
而 `tick()` 里有 `delete`（会进入 `free()`），属于**非异步信号安全**操作，在里面执行会损坏堆。
所以信号处理函数只做异步信号安全的 `send`，把真正的处理挪回主循环。
这样信号也被转成了 epoll 事件，主循环只处理一类事件——**统一事件源**。

**惰性删除**

不立即删除，攒到合适的时机再删。这个项目里有两处体现：

1. **周期性批量清理**：不是每个定时器精确触发，而是每 5 秒 `tick()` 扫一次，批量删掉过期的。
   代价是超时不够精确（最多晚 TIMESLOT），好处是不用为每个连接维护独立定时。
2. **延迟到安全时机删除**：工作线程发现连接出错时只设 `timer_flag = 1`，由主线程在下一次事件处理时
   再调 `deal_timer` 真正删除。避免工作线程删除时主线程还在用这个 fd 或定时器，导致悬空指针。

**补充：还有另一种做法**

也可以用 `epoll_wait` 的超时参数来驱动定时（`epoll_wait(..., TIMESLOT)`），不需要信号和管道，nginx 就是这么做的。
这个项目用信号 + 管道，主要是为了演示「统一事件源」。

## 6. `EPOLLONESHOT` 解决什么问题？

**一句话结论**：它保证一个连接在同一时刻只被一个线程处理——fd 触发一次后，内核把它的关注事件位清空，不再上报；
处理完必须用 `epoll_ctl(MOD)` 重新注册。

**要解决的问题：同一个连接被两个线程同时读**

在 LT 模式下，一个 fd 只要还有数据，`epoll_wait` 就会反复上报：

1. 客户端发来 8KB，fd=15 变成可读。
2. 主线程 `epoll_wait` 返回，把 fd=15 交给 worker A。
3. worker A 还没读完，主线程又一次 `epoll_wait` 返回——fd=15 **仍然可读**（缓冲区里还有数据）。
4. 主线程把 fd=15 又交给 worker B。
5. A 和 B 同时对同一个 socket 调 `recv`。

后果是数据被两个线程瓜分，HTTP 解析彻底错乱，两边都不认为请求完整。

**`EPOLLONESHOT` 怎么解决**

注册时带上 `EPOLLONESHOT` 标志。这个 fd 触发一次后，内核把 epitem 里「关心什么事件」的位清空：

- 之后的回调不再把它挂到就绪链表
- `epoll_wait` 不再返回它
- **fd、socket、连接都还在**，只是 epoll 不再盯着它

**三层东西要分清**

| 层 | 是什么 | 谁能删除它 |
|---|---|---|
| fd | 进程 fd 表里的编号 | `close(fd)` |
| socket | 内核对象，带收发缓冲区 | 引用计数归零（fd 全关、连接断开） |
| epitem | epoll 红黑树里的节点，记录「关心哪些事件」 | `epoll_ctl(DEL)` |

`EPOLLONESHOT` 只动第三层的「事件位」，**不是删 fd，也不是删 socket**。

**代价：必须手动重新注册**

被摘掉之后如果不重新注册，这个连接就再也收不到任何事件。所以每个处理结束的地方都要调 `modfd()`：

```c
void modfd(int epollfd, int fd, int ev, int TRIGMode)
{
    ...
    event.events = ev | EPOLLONESHOT | EPOLLRDHUP;
    epoll_ctl(epollfd, EPOLL_CTL_MOD, fd, &event);   // MOD = 重新注册
}
```

五个调用点：

| 位置 | 时机 | 改成 |
|---|---|---|
| `http_conn.cpp:709` | 数据没读全，回去等更多 | `EPOLLIN` |
| `:717` | 响应拼好了，等可写 | `EPOLLOUT` |
| `:536` | 没有数据要发 | `EPOLLIN` |
| `:549` | 写不下（EAGAIN），等下次可写 | `EPOLLOUT` |
| `:573` | 发完了，等下一个请求 | `EPOLLIN` |

**忘了重新注册会怎样**

不是断开，是**假死**：TCP 连接还在，但 fd 不在 epoll 里了，永远不会有新事件。
客户端一直等到超时；服务器日志一切正常，直到 5 分钟定时器兜底把它关掉。

（这和 ET 下「没读完就没人再通知」是同一类现象——**连接还在，但再也等不到事件**。）

**项目里谁加了**

```c
// http_conn.cpp:119  连接 socket：加
addfd(m_epollfd, sockfd, true, m_TRIGMode);        // true = oneshot

// webserver.cpp:160  监听 socket：不加
utils.addfd(m_epollfd, m_listenfd, false, m_LISTENTrigmode);
```

监听 socket 不加，因为只有主线程一个线程在做 `accept`，没有竞争；加了反而每 accept 一次就要重新注册，纯属浪费。

**和 ET 的区别**

| | 目的 | 解决什么 |
|---|---|---|
| ET | 减少通知次数 | **性能**：同样的数据不重复上报 |
| `EPOLLONESHOT` | 同一时刻只有一个线程处理 | **正确性**：避免多线程抢同一个 fd |

两者可以叠加：本项目在 ET 模式下，连接 fd 同时带 `EPOLLET` 和 `EPOLLONESHOT`。

## 7. HTTP 怎么判断请求读完了？粘包怎么处理？

**一句话结论**：HTTP 用「空行 + `Content-Length`」定义消息边界；这个项目用一个三段状态机逐行解析，
用 `m_checked_idx` 记住解析进度，没读完就返回 `NO_REQUEST` 等下一批数据，下次从断点继续。

**根本问题：TCP 是字节流，没有「消息边界」**

发送方发 100 个字节，接收方可能这样收到：

- **半包**：只收到 `"GET /hel"`，一行都不完整
- **正常**：完整的请求头加空行
- **粘包**：一次收到两个完整请求

TCP 只保证「字节有序到达」，不保证「按发送次数到达」。所以边界必须由应用层协议自己定义。

**HTTP 的边界怎么定**

| 部分 | 边界 |
|---|---|
| 请求行 + 头部 | 以**空行**（`\r\n\r\n`）结束 |
| 消息体 | 由头部的 `Content-Length` 指定长度 |

所以「请求读完」= 头读完 +（如果有 body）body 也读够。

**实现：三个状态 + 四个索引**

状态（`CHECK_STATE`）：

    请求行(REQUESTLINE) → 头部(HEADER) → 消息体(CONTENT，只有带 body 才进入)

索引（都在 `m_read_buf` 上，缓冲区大小 2048）：

| 索引 | 角色 | 谁移动它 |
|---|---|---|
| `m_read_idx` | **写指针**：已读入的字节数 | `recv` 之后累加 |
| `m_checked_idx` | **读指针**：解析走到哪 | `parse_line()` 每扫一字节 +1 |
| `m_start_line` | 当前行的起点 | 每切出一行后更新 |

**关键**：`recv` 把新数据追加到 `m_read_buf + m_read_idx`，**不是** `m_checked_idx`。
追加到 `m_checked_idx` 会把还没解析的数据覆盖掉。

**解析流程**

`process_read()`（`:342`）循环调用 `parse_line()`（`:164`）：

- `parse_line()` 从 `m_checked_idx` 往后找 `\r\n`
  - 找到 → 把 `\r\n` 改写成 `\0\0`，返回 `LINE_OK`
  - 找不到 → 返回 `LINE_OPEN`（数据不够，退出去等）
- 每切出一行，就按当前状态交给对应的解析函数：
  - `CHECK_STATE_REQUESTLINE` → `parse_request_line()`（`:242`），拆出方法、URL、版本
  - `CHECK_STATE_HEADER` → `parse_headers()`（`:290`），逐个读 header
  - `CHECK_STATE_CONTENT` → `parse_content()`（`:330`），等够 body

**怎么判断头结束**

`parse_headers()` 里，如果这一行是空行：

```c
if (text[0] == '\0')                 // 空行 = 头结束
{
    if (m_content_length != 0) {
        m_check_state = CHECK_STATE_CONTENT;   // 有 body，继续等
        return NO_REQUEST;
    }
    return GET_REQUEST;               // 没有 body，请求完整
}
```

**body 怎么判断读够**

`parse_content()` 靠 `Content-Length` 算：

```c
if (m_read_idx >= (m_content_length + m_checked_idx)) {
    text[m_content_length] = '\0';
    return GET_REQUEST;
}
return NO_REQUEST;
```

不是靠分隔符，是靠**长度**。

**半包怎么处理（核心）**

不重来，从断点继续：

1. 第一次 `recv` 读到 `"GET /hello HT"`，`m_read_idx` 增加，`m_checked_idx` 仍是 0。
2. `parse_line()` 找不到 `\r\n`，返回 `LINE_OPEN`，`process_read()` 返回 `NO_REQUEST`。
3. `process()` 里调用 `modfd(EPOLLIN)`，继续等数据。
4. 第二次 `recv` 把新数据**追加到 `m_read_idx` 之后**。
5. `parse_line()` 从 `m_checked_idx`（还是 0）继续扫，这次找到了 `\r\n`，正常解析。

**`m_checked_idx` 就是「看到哪儿了」的书签，有它就不用每次从头解析。**

**粘包：这个项目不支持 pipelining**

如果一个 `recv` 读到两个完整请求：

1. 第一个请求解析完，`parse_headers` 返回 `GET_REQUEST`。
2. `process_read` 立刻 `return do_request()`。
3. 响应发完后如果是 keep-alive，调 `init()`。
4. **`init()` 里 `m_read_idx = 0` 并且 `memset(m_read_buf, 0, 2048)`**。
5. **第二个请求被清掉，没有处理。**

所以这个项目**不支持 HTTP pipelining**（一条连接上连续发多个请求不等响应）。
真实浏览器基本不用 pipelining，影响不大，但严格说是一个局限。

**还有一个限制：缓冲区只有 2048 字节**

```c
static const int READ_BUFFER_SIZE = 2048;    // http_conn.h:33

// read_once() 开头
if (m_read_idx >= READ_BUFFER_SIZE) return false;    // 超了直接拒绝
```

请求（请求行 + 头部）超过 2048 字节，`read_once` 返回 `false`，连接被关闭。
头部特别长（比如超长 Cookie）的请求会被拒。

## 8. 压测多少 QPS？瓶颈在哪？

**一句话结论**：3950 QPS 左右（100 并发、10 秒）。瓶颈是**主线程**——默认的 Proactor 模式没有用操作系统的异步 I/O，
`accept` / `recv` / `writev` / `close` 全部由主线程同步执行，工作线程只做解析。

**测试方法**

`run.sh` 一键完成：编译 → 后台启动服务器 → 压测 → 结果写入 `bench.txt` → 退出时用 `trap` 自动关闭服务器。

```bash
./run.sh     # 内部执行 webbench -c 100 -t 10 http://127.0.0.1:9006/
```

环境：VMware 里的 Ubuntu，16 个 vCPU，客户端和服务端在同一台机器上。

**数据**

| 配置 | QPS | 说明 |
|---|---|---|
| 日志开 | 3019 | 基线 |
| 日志关 | 3116 | 只涨 3%，日志不是瓶颈 |
| 日志关 + 丢弃 stderr | 3965 | **+27%**，主要提升来源 |
| 工作线程 8 → 16 | 3937 | 无变化 |
| listen backlog 5 → 128 | 4068 | 无变化（在噪声范围内） |

**怎么做的**：控制变量法——负载、并发、时长、URL 全不变，每次只改一个参数。

**三条独立证据指向「主线程是瓶颈」**

1. **加线程无效**：工作线程从 8 加到 16，QPS 从 3965 变成 3937，在噪声范围内。
   如果瓶颈在工作线程，加线程应该变快；没变，说明工作线程本来就在闲着。
2. **去掉主线程的负担就变快**：`fprintf(stderr, "[READ]/[WRITE]")` 是在主线程里执行的
   （`dealwithread` / `dealwithwrite` 由 `eventLoop` 调用），去掉之后 QPS 涨 27%。
3. **直接观测到 accept 队列积压**：压测时用 `ss -lnt` 看监听 socket 的 `Recv-Q`，一直顶在 96～97（上限 128），
   说明主线程的 `accept` 速率跟不上客户端的连接速率。

**为什么加 backlog 没用**

`Recv-Q` 接近上限说明「有人在排队」，但**队列满不等于队列是瓶颈**——队列是被「主线程 accept 慢」喂满的。
加宽等候区只是让更多人站着等，柜台出餐速度没变。

**优化方向**

- `SO_REUSEPORT`：多个线程各自 `socket → bind → listen` 同一端口，内核按四元组哈希分流，accept 就并行了（nginx 的做法）。
- `accept4()` 代替 `accept` + `fcntl`，省一次系统调用。
- 把读写也交给工作线程（真正的 Reactor），或用 `io_uring` 做真正的 Proactor。
- 定时器从升序链表换成最小堆，把 `add_timer` 从 O(n) 降到 O(log n)。

**一个方法论上的注意**

单次压测的波动大约在 ±3%，所以 2% 的差异不能当作「提升」。
判断「有没有变化」，要么多跑几次取范围，要么差异超过噪声。

# 附录：基础概念速查

> 看上面的答案卡住时，先来这里查词，再回去看题。

## 进程与线程

- **进程**：运行中的程序，有自己的内存空间。`./server` 就是一个进程。
- **线程**：进程内的一条执行流，共享进程的代码和全局数据，各自有独立的栈。
- 这个服务器是「1 个主线程 + 8 个工作线程」：主线程跑 `main → eventListen → eventLoop`，工作线程跑 `threadpool::run()`。

## fd（文件描述符）

- 进程打开文件、套接字或管道时，内核分配一个整数编号，这就是 fd。
- **fd 只是进程 fd 表里的一个索引，不是连接本身。**
- 0 / 1 / 2 固定是 stdin / stdout / stderr，之后按分配顺序递增。

## 连接是怎么建立的：listen / accept / accept 队列 / backlog

1. `socket()` 创建套接字，`bind()` 绑定端口，`listen()` 把它切成被动模式，开始接收连接。
2. **三次握手由内核完成**，不是你的程序做的。
3. 握手完成的连接会进入 listenfd 的 **accept 队列**。
4. `accept()` 从队列里取一条，**内核为它创建新 socket，返回新的 fd（connfd）**。
5. listenfd 只负责「收客」，connfd 才是这条连接收发数据的通道。两者共用同一个监听端口，靠四元组区分。
6. `listen(fd, backlog)` 的 `backlog` 是 accept 队列的最大长度。本项目是 128（原来 5）。

## 阻塞 / 非阻塞 / 同步 / 异步

- **阻塞**：调用不返回，线程睡在那里。
- **非阻塞**：调用立刻返回；没数据时返回 `-1` 且 `errno == EAGAIN`。
- **同步**：调用返回时，结果已经在手上。
- **异步**：调用立刻返回，结果稍后由回调或事件交付。

| 组合 | 例子 |
|---|---|
| 同步阻塞 | 普通 `recv` 读阻塞 socket |
| 同步非阻塞 | `recv` 读非阻塞 socket（本项目 + epoll） |
| 异步 | `io_uring`（本项目没用） |

## 回调函数

- 把**函数的地址**存进结构体，别人在需要的时候拿这个地址去调用。
- **登记时不执行，触发时才执行。**
- 语法：`typedef void (*callback_t)(int);` —— `callback_t` 是类型，`callback_t f;` 里的 `f` 才是变量。
- epoll 在注册时把 `ep_poll_callback` 挂到 socket 的等待队列上；数据到达时内核执行它。

## 等待队列

- 每个能等待的对象（socket、管道）都有一条等待队列，记录「谁在等我状态变化」。
- 线程读不到数据时，把自己挂进去睡；数据来了，内核遍历队列把大家叫醒。
- **注意**：epoll 的就绪链表、信号量的等待队列、socket 的等待队列，是三样不同的东西。

## epoll 的三个部分

| 部分 | 装什么 | 谁维护 |
|---|---|---|
| 红黑树 | 所有注册过的 fd | 内核 |
| 就绪链表 | 已经就绪的 fd | 内核（回调挂进去） |
| 等待队列 | 挂在每个被监控 fd 上的回调 | 内核 |

`epoll_wait` 只碰就绪链表，所以开销与总连接数无关。

## fd / socket / epitem 三层

- **fd**：进程 fd 表里的编号，`close(fd)` 才消失。
- **socket**：内核对象，带收发缓冲区和 TCP 状态，引用计数归零才释放。
- **epitem**：epoll 红黑树里的节点，记录「这个 fd 我关心哪些事件」。

`EPOLLONESHOT` 只清空 epitem 的事件位，不动 fd 和 socket。

## ET / LT

- **LT（水平触发）**：条件成立就一直报（报告后把「还有数据」的 fd 放回链表）。
- **ET（边沿触发）**：只在状态变化那一刻报一次，之后要等新数据。
- ET 必须循环读到 `EAGAIN`，且 fd 必须非阻塞。

## 信号

- **信号是内核给进程的异步通知**，只有一个编号（`SIGINT`=2、`SIGALRM`=14、`SIGTERM`=15）。
- `alarm(n)` 只是「预约」：n 秒后内核发出 `SIGALRM`。
- 收到信号后的处理方式：默认动作（多数是终止）、忽略、执行你注册的处理函数。
- **信号处理函数里只能调异步信号安全的函数**（`write`/`send` 可以，`malloc`/`free`/`printf` 不行）。

## 管道（本项目的 socketpair）

- 内核里的一块缓冲区 + 两个 fd（一端写、一端读）。
- 因为两端都是 fd，**可以被 epoll 监控**。
- 本项目用它把「信号到了」转成「某个 fd 可读了」——这就是统一事件源。

## 信号量（sem）

- 一个整数 + 一个等待队列。
- `post()` 值 +1；`wait()` 值 -1，减完为负数就睡。
- **值 < 0 时，绝对值 = 正在等待的线程数**；值 > 0 时，值 = 可用的资源数。
- 本项目两处用法：线程池（值 = 待处理任务数，初始 0）、连接池（值 = 可用连接数，初始 8）。

## 互斥锁

- 保证一段代码同一时刻只有一个线程能进（临界区）。
- 用在 `std::list` 的 `push_back` / `pop_front` 上：不加锁会破坏链表指针。

## 线程池

- 固定数量的线程 + 一个任务队列。主线程放任务，worker 取任务。
- 好处：避免频繁创建销毁线程；用队列解耦生产者和消费者。
- 本项目：8 个线程，队列上限 10000，用信号量唤醒。

## Reactor / Proactor

- **Reactor**：通知「可以读了」，处理者自己 `recv`。
- **Proactor**：通知「已经读好了」，数据由操作系统搬。
- 本项目名义上是 Proactor，但因为没用 OS 异步 I/O，变成「主线程替 worker 读」。

## 最小堆

- 用数组存的完全二叉树，每个节点都不大于它的子节点，所以**根是最小值**。
- 索引关系：节点 `i` 的孩子是 `2i+1` 和 `2i+2`，父亲是 `(i-1)/2`。
- 插入和取最小都是 O(log n)。
- 适合「总想拿最早到期的那个」的场景（定时器）；本项目实际用的是升序链表。
